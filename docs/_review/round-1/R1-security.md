# R1 — Independent Security Review (adversarial)

**Project:** Saman ERP (`F:\harness\saman-erp`) · **Round:** 1 · **Reviewer:** independent application-security reviewer (OWASP ASVS L2, API security, multi-scope authorization) · **Date:** 2026-10-19
**Inputs read:** `00-overview/README.md`, `01-architecture/ARCHITECTURE.md` (§9/§10/§13), ADR-0004/0005/0006/0008/0010/0012, `04-security/SECURITY.md`, `04-security/THREAT-MODEL.md`, `03-api-contract/API.md` (§1.4/§1.12/§1.17/§2/§4/§5/§6/§7/§8), `02-data-model/DATA-MODEL.md`, `erp-docs/limo-sms.txt`, `erp-docs/digikala-api.txt`.
**Method:** claims in SECURITY/THREAT-MODEL were treated as untrusted and cross-checked against API, DATA-MODEL, ADRs and the real partner contracts. Only defects with a concrete exploit path are listed; well-specified controls are in *Verified controls*.
**Repository state check:** `apps/`, `packages/`, `scripts/`, `infra/` contain **0 files**; only docs/config skeleton exist.

Severity legend: **Blocker** = must be fixed before P1 implementation starts / release gate; **High** = exploitable privilege, money, PII or availability impact; **Medium** = needs a precondition or weaker impact; **Low** = hardening/spec hygiene.

## Verified controls

Checked against the contract and data model; these are well specified (implementation still unverified — see B-01):

1. **Argon2id profile + calibration + rehash-on-login**, PHC strings, no hash in logs/audit (`SECURITY.md` §2.1).
2. **Refresh rotation with family reuse detection**, hashed token (`auth_sessions.refresh_token_hash` UNIQUE), 10 s grace window, family revoke + security event (`ADR-0004`, `SECURITY.md` §2.2, `DATA-MODEL.md` line 258–259).
3. **Refresh cookie attributes**: `__Secure-` prefix, `Path=/api/v1/auth`, HttpOnly/Secure/SameSite=Lax, host-only; business endpoints bearer-only; `/auth/*` Origin + custom header + JSON content-type (`SECURITY.md` §6.2/§6.4, `API.md` §1.17).
4. **OTP construction**: 6-digit CSPRNG, 2-min TTL, HMAC(pepper, mobile:purpose:code), constant-time compare, 5 attempts, single-use, send limits, purpose binding in the hash (`SECURITY.md` §2.4).
5. **Anti-enumeration for OTP request/login failure** (constant 202, padded delay, generic errors) (`SECURITY.md` §2.4/§2.3, `API.md` §1.16).
6. **Permission cache keyed by `pv`** with DB read-through and same-transaction version bump; forged cache entry grants nothing (`SECURITY.md` §3.3).
7. **Serializer-level cost/margin/PII stripping** applied to lists, details, exports, dashboard widgets and audit diffs; no client-side masking (`SECURITY.md` §3.4, `API.md` §10.3).
8. **SQL injection posture**: Drizzle parameter binding, enum→column identifier map for sort/filter, banned `sql.raw`/`unsafe()` via lint/Semgrep, `saman_app` has no superuser/file functions (`SECURITY.md` §4.2).
9. **XSS posture**: React escaping, no `dangerouslySetInnerHTML`, plain-text rich content, strict CSP `script-src 'self'`, SVG uploads rejected (`SECURITY.md` §4.3/§4.4.3, §6.5).
10. **CSV formula-injection escaping** for cells starting `= + - @ \t \r`; XLSX import reads values only with `cellFormula:false` (`SECURITY.md` SEC-OUT-06 line 292, §4.4.8).
11. **Upload admission**: per-purpose size caps, magic-byte match, extension/MIME cross-check, `sharp` re-encode with EXIF strip, server-generated object keys, private bucket, `Content-Disposition: attachment` + `nosniff` + sandbox CSP, 5-min presigned download (`SECURITY.md` §4.4, `API.md` §7.1).
12. **Inbound webhook mechanics**: raw-body MAC over exact bytes, `timingSafeEqual`, ±300 s skew, unique `(channel, external_event_id)`, async-only processing, fetch-back before money/stock effects, unknown event types rejected (`SECURITY.md` §4.6, `API.md` §6.1/§6.3).
13. **Ledger/journal immutability**: append-only grants, `SECURITY DEFINER` post/void functions, period lock, posted-entry trigger, deferred balance trigger, nightly consistency check (`SECURITY.md` §8.2, `DATA-MODEL.md` §5.1/§5.6).
14. **Credential envelope crypto**: AES-256-GCM, 12-byte random IV, AAD binding org/table/id/field, versioned keyring, `kid` rotation, re-encrypt runbook, decryption confined to adapter scope (`SECURITY.md` §5.2–§5.4).
15. **Backup encryption**: `age` to an offline recipient before upload, write-only bucket identity, object lock, restore-drill verification (`SECURITY.md` §5.5/§8.3).
16. **Log redaction + no-secret assertions**: pino redact paths, `LOG_BODIES` forbidden in production, no `console.log`, secret-pattern scrub on third-party errors (`SECURITY.md` §5.6).
17. **Boot guards**: production refuses `SMS_MODE!=live`, `LOG_BODIES=true`, `DOCS_ENABLED=true`, invalid keyring, weak/short keys, superuser `DATABASE_URL`, missing `PUBLIC_ORIGIN` (`SECURITY.md` §17.1 line 1299).
18. **Pagination/DoS bounds**: cursor/offset caps, `limit≤500`, `perPage≤200`, deep-offset rejection, shallow include depth, date-range requirement on partitioned tables (`API.md` §1.5–§1.7).
19. **Body/header caps** (1 MiB JSON, 10 MiB bulk, 25 MiB multipart, 2 MiB webhook) and Fastify/edge timeouts (`SECURITY.md` §4.1, `API.md` §1.17/§6.3).
20. **Digikala/Limo contract realities**: Limo `ApiKey` header and `sendpatternmessage` with `ReplaceToken`/`OtpId` match `limo-sms.txt`; Digikala token/refresh/revoke + 264-endpoint scope catalog match `digikala-api.txt`; correctly marked `TBD-*` where schemas/signatures are absent rather than guessed (`API.md` §8.2–§8.4).

## Verdict

**Not releasable — documentation-level blockers.** The security *catalogue* is unusually thorough and many controls are specified to an implementable level (see *Verified controls*), but as of this baseline there is no implementation at all, and the surrounding docs claim otherwise (B-01), so "verified" cannot mean anything yet. More importantly, six design defects are exploitable paths, not documentation nits: device-trust MFA bypass (B-02), admin/self-service password-reset takeover (B-03), defeatable maker-checker via mutable approval config (B-04), an audit trail that cannot be tamper-evident (B-05), and an authorization model whose two normative registries disagree (B-06). The High set adds several one-permission-to-full-data paths (exports, reports/dashboards, outbound webhooks, file downloads, channel logs) and a credential-handling posture (`env_file` + docker sudo) that contradicts the stated least privilege.

**Minimum conditions to exit round 1:** (1) B-01 corrected with real evidence links; (2) B-02/B-03 rewritten auth contracts with server-issued device secrets and a single reset policy; (3) B-04 SoD enforced by DB constraints plus approval-governed config; (4) B-05 hash-chain schema + grants + event vocabulary; (5) B-06 one generated permission registry; (6) H-02/H-03/H-04/H-06 closed by endpoint-contract changes (per-entity permission checks and allowlists), since each is a direct PII/finance exfiltration path. All Medium items should be closed before the corresponding module phase (M-01/M-02/M-08 before P1; M-03–M-05 before P5; M-09/M-10 before P2).
