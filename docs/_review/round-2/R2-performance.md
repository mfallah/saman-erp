# R2 — Performance & Scalability Review (Saman ERP)

**Reviewer:** R2-P (independent) · **Date:** 2026-10-19 · **Scope:** ARCHITECTURE v1.1 §6/§7/§11/§13, ADR-0007/0009/0010/0013, DATA-MODEL v1.1, API v1.1, TESTING §12.

**Method:** read-only design review; no runtime measurements were possible (P1 code is skeleton only — `apps/api/src` has pool/pagination/metrics scaffolding but no inventory, outbox, channel or reporting implementation). Every "impact" number below is an **estimate derived from the stated envelope** (50k orders/day peak 20 orders/s, 2M ledger rows/day, 40k variants, 500 concurrent users, 500 reads/s) plus row/index widths from the documented DDL. Assumptions are stated so implementation can falsify them in the benchmarks in the last section.

**Envelope used for all arithmetic**

| Factor | Value | Source |
|---|---|---|
| Orders | 20/s peak (3 lines each) → 60 line writes/s | ARCHITECTURE §11, TESTING §12.1 |
| Ledger | 2,000,000 rows/day ≈ 23.1 rows/s average; 3× peak ≈ 70/s | ADR-0009, DATA-MODEL §4.1 |
| Reads | 500 req/s sustained, 2,000/s headroom target | TESTING §12.1 |
| Variants / balances | 40,000 variants, 120,000 balance rows | TESTING §12.3 |
| Channel mappings | 80,000 (2 accounts × 40k) | TESTING §12.3 |
| Host | 8 vCPU/16 GB recommended; PG 2–4 CPU / 4–6 GB `shared_buffers`; disk 250–500 GB NVMe | DEPLOYMENT §5 sizing table |
| Redis | 512 MB, `maxmemory-policy noeviction` | DEPLOYMENT §5, compose |

**Findings:** 7 Blockers · 11 High · 10 Medium + 6 observability gaps · 7 Low (41 total).

**Round-1 overlap rule:** R1 findings are not restated. Where a R1 fix created a *performance* consequence, the finding says so explicitly (noted `[R1-… follow-on]`).

| **H-01** | No `lock_timeout` and a naive 3-retry wrapper: under contention, requests wait the full 5 s and all losers retry simultaneously | `statement_timeout=5s` applies to lock waits. ## Capacity verdict

**Can the single-host envelope hold? No — not as specified.** The *OLTP* envelope is credible; the *data lifecycle and background-plane* envelope is not.

What holds on 8 vCPU / 16 GB (PG 2–4 CPU, 4 GB `shared_buffers`):

- **60 stock line writes/s** (20 orders/s × 3) is well within a single PostgreSQL if the transaction is short: the arithmetic (≈60 row updates/s + 180 index writes/s) is ~2–4 % of a 4-core box. Product/barcode lookup by unique index + 60 s cache at 500 reads/s is also fine **once B-01/H-11 indexes exist**.
- **2M ledger inserts/day** (23/s avg, ~70/s peak) with 7 B-trees is feasible on NVMe (~1.2 GB/day heap+index, ~3–4 GB/day WAL) — but only if the read/retention plan stops accumulating the other tables.

What does **not** hold:

1. **Disk.** At the stated headroom the hot ledger alone is ~200–250 GB/6 months; adding unsampled `api_request_logs` (≈1.8 TB/90 d at 500 rps), `channel_api_calls` with jsonb payloads (≈230 GB/180 d), `outbox_events` 30 d (~40 GB), 12 hot months of `audit_logs` (≈100–150 GB), WAL and local backups puts the requirement at **3–12 TB**, i.e. 6–40× the 250–500 GB host. No retention tweak fixes the request-log and channel-call tables; they must be sampled/narrowed.
2. **Background plane.** A 100-event/s single-batch outbox dispatcher is at or under peak demand (120–180 events/s), and a 512 MB `noeviction` Redis shared by jobs/cache/rate-limits will OOM during the first full catalog sweep. Both are hard ceilings on "stock push < 5 s p95".
3. **Maintenance window.** Full-window consistency scans + full `pg_dump` + 10 partition DDLs + 3 matview refreshes all run between 02:00–03:30 on a 2–4 CPU PostgreSQL; the first three cannot finish and will evict the cache and/or block writes (`lock_timeout` absent).
4. **Burst behaviour.** 100 concurrent allocators on one variant will queue to ≈2 s p95 with the documented "lock all locations + hold the numbering row" design; the 500 ms budget and "0 × 5xx" gate in LOAD-06 will fail on the first CI run.

**Minimum changes to make the envelope hold:**

| # | Change | Unblocks |
|---|---|---|
| 1 | Sample/narrow request and channel-call logs; 14-day daily partitions; stdout as the full log | Disk, B-04 |
| 2 | Hot ledger 3 months + warm archive (not 6+25); off-host incremental backups (pgBackRest) | Disk/RTO, B-07 |
| 3 | Conditional `UPDATE … WHERE available >= qty` in canonical order; `lock_timeout`; number blocks pre-allocated | B-02, H-01 |
| 4 | Two-phase outbox claim + 16–32 parallel handlers + 3-day poll bound | B-03 |
| 5 | Redis split (queue vs cache), job retention, batch-per-account sync jobs | B-05, B-06, H-08 |
| 6 | Ordered per-partition indexes `(created_at, id)`; cursor on internal `(created_at, id)`; partial work-queue indexes | B-01, H-11 |
| 7 | Incremental consistency watermarks; incremental matview rollups; export streaming | B-07, H-05, H-06 |
| 8 | PgBouncer at 2 replicas + per-class pool/timeout budgets | H-07 |

With items 1–5 alone, the design becomes **conditionally feasible at the stated peak** provided the 100-parallel single-variant benchmark passes after item 3 and outbox lag p95 < 5 s is demonstrated at 2× peak. Without them, the honest capacity statement is ~200k ledger rows/day and ~10 orders/s.
